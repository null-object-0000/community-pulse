> 一个便携的 MCP 服务器，把 Claude Code / OpenCode 的 AskUserQuestion 工具以兼容形状暴露出来。Codex 接上后，Agent 提问就能弹原生表单、选项点一下就走，不再退化成纯文本对话。默认只走 MCP elicitation，兜底 provider 必须显式开启。 为什么做这个项目？ 最近我越来越喜欢用 grilling 这条路子开发——Agent 在动手前，一件事一件事地逼我，把"大概是这样"逼成"确定就是这样"。 这套体验在不同工具里落差很大： 在 Claude Code 和 OpenCode 里，有内置的 AskUserQuestion：带标题、带选项、带推荐项，点一下就回去了。 在 Codex 里没有这个工具。Agent 只能把问题打印成一坨文本，我再自己打字回答。对 grilling 这种高频追问的工作流，体验是断裂的——选项没法点、推荐项糊成一团、节奏退化为"读—想—敲"。 差的不是"能不能问"，而是问与答之间的摩擦。一次问答没感觉，二十次下来就是舒服和难受的差别。 于是我把这个工具以 MCP 服务器的方式补了回来，让两边行为对齐。 核心亮点 | 亮点 | 说明 | ||| | 与 Claude Code 形状兼容 | 输入/输出结构与原生 AskUserQuestion 一致：questions 1–4、options 2–4、含推荐项、支持 multiSelect。 | | 默认只走原生 elicitation | auto provider 仅使用客户端本机的 MCP 表单 UI，不会偷偷开终端、弹浏览器或桌面框。 | | 兜底必须显式 | terminal provider 需在配置里点名启用；写提示时绕开 stdout，不污染 MCP 的 stdio。 | | 失败状态分得清 | answered / cancelled / declined 三态返回，多问题全有或全无，不给 Agent 留残留数据去猜。 | | 一行 npx 即用 | 无需装包，无需密钥，无需账号。 | 一个必须说的坑 Codex 需要显式放行 MCP elicitation，否则工具调用会直接拿到 declined，根本不弹窗。把 mcpelicitations 在 granular approvalpolicy 里打开： toml approvalpolicy = { granular = { sandboxapproval = true, rules = true, mcpelicitations = true, requestpermissions = true, skillapproval = true } } 另外，不要在需要提问的场景里用 codex yolo。yolo 会绕过审批，而 Codex 把 MCP elicitation 当作需用户确认的提示——在这种模式下，表单出现之前就可能被自动拒绝。 如果你要"文件/命令随便跑，但用户提问还是要弹窗"，应该只放宽沙盒、保留 elicitation： bash codex sandbox dangerfullaccess c 'approvalpolicy={granular={sandboxapproval=true,rules=true,mcpelicitations=true,requestpermissions=true,skillapproval=true}}' 使用场景 在 Codex 里跑 grilling / grillme 工作流，让 Agent 一项一项追问时，每问都能弹结构化表单。 在不开 yolo、又希望 Agent 在关键决策点先求证的协作流里。 给其它不支持 AskUserQuestion 但支持 MCP elicitation 的客户端兜一个一致的提问工具。 链接 GitHub: 作者博客: 介绍文章: 作者自荐 我是 Sanjeev，后端开发者，平时主要在 Codex / Claude Code / OpenCode 三个 CLI 之间来回切换。这个工具是我自己日常在用的，目的是把 grilling 这条路子从"只能在 Claude Code / OpenCode 用"扩到"Codex 上也照样用"。如果觉得有用，欢迎 Star 支持一下。

Token 上限时进行平滑的自适应压缩，既能保证模型的逻辑连贯性，又将 Payload 体积强力缩减数倍，极大地节约了上游额度。 4. 📍 Map Local 规则级本地 Mock 管线 问题：现代 AI 客户端在启动或运行时极其嘈杂。比如 Claude Code 在每次运行时会偷偷发送遥测数据（telemetry）、频繁去服务器查询最新版本并发出 Vertex AI 的 maxtokens: 1 ### 【开源自荐】灵犀BI：一个会"自我进化"的AI驱动BI平台——告别手写SQL，让数据自己开口说话 👤 bonfirer
> 灵犀BI：一个会"自我进化"的AI驱动BI平台——告别手写SQL，让数据自己开口说话 如果你的团队还在为"这个指标到底怎么算"反复对齐口径，还在等数据组排期出报表——那么这篇文章值得你花 8 分钟读完。 一、你大概率正在经历的三个痛点 痛点 1：数据"有"，但"用不上" 公司早已上了 MySQL、PostgreSQL 甚至 2024 年以来，各种"自然语言查数据库"的工具层出不穷。但它们都有一个共同的问题：无状态。你问一次，它答一次，下次问类似问题（哪怕只是换个时间范围），它从零开始推理——完全记不住你上次纠正过的业务定义。每一次对话都是一次全新的猜谜游戏。 二、灵犀BI 的方案：让 BI 从"工具"变成"同事" 灵犀BI（LingxiBI） 是一个开源 AI 驱动的 BI 平台。它解决的问题不是"能不能用自然语言查数据"——这个门槛已经被大模型拉得很低了。它解决的是更根本的问题：如何让 AI 持续理解你的业务，越用越准，最终成为团队里那个"最懂数据的同事"。 核心理念就一句话：接入数据库，与数据对话，让 AI 为你构建看板。 工作流极其简单： 接入数据源 → 用自然语言提问 → AI 生成 SQL 并执行 → 一键生成看板 → 持续迭代优化 不需要手写一行 SQL，不需要配置数据模型，不需要学习任何 BI 工具。 三、核心优势拆解：为什么它跟别的 texttoSQL 不一样？ 优势 1：自学习机制——越用越聪明（这是真正的差异化护城河） 大多数 texttoSQL 工具是"问完即焚"的。灵犀BI 的杀手锏在于每一次对话都变成下一次回答的燃料。 你提问 → AI 回答 → 后台自动提炼新增业务知识 → 存入知识库（按数据源隔离）→ 下次回答时智能召回 → 下一次回答更准确 具体来说，这个闭环包含四层知识沉淀： | 知识层 | 说明 | 价值 | |||| | 知识库 | 表关系、字段含义、业务规则 | 让 AI 理解你的数据模型 | | Fewshot 示例 | 你对好回答点 👍，存为标准示例 | 模型下次严格遵循 | | 精选指标库 | 验证过的命名 SQL 定义 | 可复用的高可信定义，杜绝口径漂移 | | 列画像 | 枚举值、数值范围、数据样本 | AI 写 SQL 时更精准的过滤条件 | 人在回路的设计也很巧妙：对一次满意的回答点个 👍，系统自动把它转成 fewshot 示例——不需要你写任何规则或配置。这是真正的"无感训练"。 优势 2：AI 看板——一句话生成，对话式迭代 传统 BI 的看板搭建流程是：选图表类型 → 绑定数据源 → 配置维度/指标 → 调样式 → 发布。熟练工 30 分钟，生手半天。 灵犀BI 的流程是：对着聊天框说一句话。 比如： "帮我生成一个按月份统计各渠道销售额的趋势看板，加上环比增长率。" AI 直接给你一个基于 ECharts 的响应式 HTML 看板。不满意？继续对话调整——"把柱状图换成折线图"、"加上去年同期对比"、"把配色改成我们品牌色"。每次修改都有完整的版本历史，随时可以回滚到任意历史版本。 看板的视觉风格（配色、排版、图表样式）还能存为可复用主题，下次一键套用。 优势 3：不只是看数据——预警 + 分析，形成完整闭环 很多 BI 工具的核心问题是：看板建好了，但没人天天盯着看。 灵犀BI 补上了"从看到做"的最后一公里： 多渠道预警：设定阈值规则 → 触发后 AI 自动撰写预警内容 → 通过邮件（附带 Excel 附件）+ 飞书交互卡片（HMACSHA256 加签）双通道推送。你不需要盯着看板，数据异常会自动找到你。 AI 数据分析总结：一键生成叙述式分析——核心结论、关键发现、趋势判断、异常检测、行动建议。而且禁止 AI 编造数据，所有结论严格基于真实数据和快照趋势。 定时快照：自动采集指标快照，支撑趋势分析、同比、环比——这些都是 AI 分析总结的数据基础。 优势 4：企业级多用户权限——不像个人玩具 很多 AI 开源项目在"多用户"这件事上很敷衍。灵犀BI 的设计从一开始就是面向团队的： | 维度 | 设计 | ||| | 角色 | 管理员（管理基础设施）+ 成员（操作自己的内容） | | 内容隔离 | 报表、指标、会话、预警规则按用户隔离 | | 数据源授权 | 成员只能看到和查询被授权的数据源，服务端强制校验 | | 注册管控 | 首个注册即管理员，之后注册关闭，由管理员统一管理用户 |
