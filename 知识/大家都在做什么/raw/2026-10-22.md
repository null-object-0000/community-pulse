The loop runs on stateless workers in the control plane. Each iteration&#x27;s result commits in one transaction, so the model output, its tool calls, usage and the next wakeup are saved together or not at all. If a worker dies mid-iteration, nothing commits, its lease expires, and another worker retries it. Agents waiting on a user, a tool or a retry don&#x27;t hold a worker, so one worker can multiplex thousands of agents. Also unlike other harnesses, the machines that the workers (our agent loop) run on aren&#x27;t where the agent runs its commands. Instead, any macOS or Linux machine with an internet connection, like your laptop or any cloud sandbox, can run a small daemon (omnarad) that connects out to Omnara, so it doesn&#x27;t need any open inbound ports. The agent then gets tools for that machine, like running a command or editing a file. An agent can have any number of machines connected to it. A fun thing I like to do is I have my laptop and a cloud sandbox connected to the same agent, so when my laptop is on, my agent codes there and I can interact with it, and I have it often push to Github. ### # [开源自荐] Ops Admin 两个月更新：新增中间件管理、JumpServer 资产同步，完善作业编排和监控告警 👤 qishua
> 大家好，8 月底在 V2EX 分享过自己开发的开源运维平台 **Ops Admin**。距离上次发帖快两个月了，最近一直在结合日常运维中的需求补功能、修问题，来汇报一下进展。 - 项目地址： https://github.com/qishu321/ops-admin - 项目网站： https://qishu321.github.io/ops-admin-website/ - 上次的介绍： https://www.v2ex.com/t/1238337 简单介绍一下：Ops Admin 基于 **Go + Vue 3**，主要面向个人运维和中小型运维团队，把主机、数据库、Kubernetes 、批量执行、作业编排、监控告警和构建发布放到一个工作台里，也支持通过 SSH 网关访问内网资源。 - 项目截图 ## 界面截图 下面是这次更新后的几张界面截图，每行两张。 作业编排：条件分支与步骤配置 SSH 终端：资产树与多标签会话 服务健康诊断：Arthas Java 诊断 Kubernetes 监控详情：集群、节点与 Pod 指标 日志查询：按命名空间与关键词检索 这次主要更新了以下几个部分。 ## 1. 新增中间件管理 接入了 **RabbitMQ 、Nacos 、etcd 、ZooKeeper 和 Kafka**，提供各自的管理工作台，认证信息复用平台的凭据管理。 - **RabbitMQ**：虚拟主机、队列、交换机、绑定关系、连接和消费者查看，以及常用管理操作。 - **Nacos**：适配 2.x 、3.x ，支持配置管理、服务发现、实例上下线和命名空间管理。 - **etcd**：按路径浏览 Key 、查看和修改值、查看集群成员，支持 TLS 证书接入。 - **ZooKeeper**：节点树浏览、数据编辑、节点信息和 ACL 查看。 - **Kafka**：Topic 详情、分区与位点、消息浏览和发送、消费组、Topic 配置等。浏览消息时不加入消费组，也不提交消费位点。 这些功能主要覆盖日常排查和管理中常用的操作，还在继续完善。 ## 2. 统一资产同步入口 新增了 **JumpServer 资产同步**，可以把资产及其分组关系同步到平台的主机和主机组中。 云主机同步也集中到了资产同步页面，减少来回切换入口、重复选择配置的操作。同步时复用凭据管理，预览中会过滤已经同步且没有变化的资产。 ## 3. 完善作业编排和定时任务 重新调整了作业编排界面，并增加了**条件分支**。脚本执行、文件分发、人工确认和消息通知可以组合成作业，根据条件走不同流程。 同时优化了任务日志、脚本参数、定时任务和 HTTP 探针通知，修复重复通知等问题，让执行结果和失败原因更容易追踪。 ## 4. Kubernetes 和终端体验 这部分做了不少日常使用上的改进： - 完善集群、节点、Pod 和网络监控。 - 增加工作负载伸缩策略，优化镜像更新、环境变量查看等操作。 - 修复通过网关连接 Pod 终端的问题。 - SSH 和 Pod 终端支持 **5000 行历史回滚缓冲**，优化滚动和连接体验。 - 服务健康诊断页面切换标签后保留已有诊断状态，减少重复操作。 ## 5. 调整权限管理 整理了之前比较分散的权限入口，围绕**用户、用户组、访问策略和权限模板**组织授权。 主机、Kubernetes 、数据库、中间件等资源可以按用户或用户组授权，也补充了全局只读角色，修复了一些授权后页面需要刷新才能生效的问题。 另外新增了管理员维护的命令过滤规则，可分别作用于 SSH 终端和作业执行； Pod 终端不在过滤范围内。 ## 6. 持续完善监控告警 新增了**告警规则导入、导出**，方便备份和迁移；监控大屏支持拖拽调整面板，并继续完善数据库及 Kubernetes 监控。 最近还集中处理了一个容易被忽略的问题：**指标查不到，不一定代表故障恢复。**例如 Pod 消失后，Ready 指标也可能消失。针对这类情况，补充了无数据处理和明确恢复条件，避免仅因为查询结果为空就发出恢复通知。 --- 整体上，这两个月主要是在补齐中间件、资产同步和权限管理，同时把终端、作业执行、监控告警这些高频功能打磨得更顺手一些。 项目仍在持续迭代，欢迎感兴趣的朋友试用。遇到问题可以提 Issue ；也想听听大家的意见：**你们日常运维中，最希望统一到一个平台里的操作是什么？** 如果觉得有用，也欢迎点个 Star ，谢谢大家。

### 做了一个 PHP2Shell 应急辅助工具：被动响应头检查、版本核对和配置引导 👤 Tim99
> 最近做了一个 PHP2Shell 应急辅助网站，把公开响应头检查、PHP 版本比较和临时缓解配置整理到了一起，想分享给有 PHP 网站需要维护的朋友。 地址： https://checkphp2shell.com/ 目前主要有几个功能： - 输入公开域名，查看响应头是否暴露 PHP 版本，以及是否存在 PHP 、Laravel 、WordPress 等相关线索。 - 识别 Cloudflare 、Sucuri 、Akamai 、CloudFront 等边缘服务的公开标记。 - 手动输入实际 PHP 版本，核对修复版本门槛，并查看不同部署环境的配置示例。 - 提供 php.ini 、Nginx 、Apache 、Cloudflare WAF 、ModSecurity 、Docker/K8s 的配置引导。 想先把检测边界讲清楚：**它检查的是公开响应头，结果只能作为排查线索。** 对目标网站只发送普通 HEAD 请求，遇到明确不支持 HEAD 的响应时才回退 GET ，不发送漏洞利用载荷或 multipart POST ，也不跟随重定向。 响应头可能被隐藏、修改或缓存，因此： - 没有发现 PHP 特征，不能证明网站没有使用 PHP 。 - 显示的版本达到修复门槛，不能确认实际软件包和所有 Web worker 都已更新。 - 发现 Cloudflare 等标记，不能确认 WAF 已启用，更不能确认规则能够覆盖相关攻击。 - 外部检查无法读取内部 php.ini ，也无法确认网站此前是否遭到入侵。 另外，页面里刻意区分了**临时缓解和完整修复**。 INI 配置和 WAF 规则可以在适用条件下降低部分攻击路径的风险，但不能当成完整修复。完整修复仍需要应用官方修复版本或经厂商确认的安全补丁，并验证实际处理 Web 请求的 PHP 实例和 worker 都已经使用修复后的构建。CLI 的 `php -v` 也可能与网站实际运行的 PHP 不同。 配置生成前需要重新确认版本、部署方式和适用前提，响应头里的版本不会自动被当成已经核实的服务器环境。 网站目前支持英语、日语、德语、西班牙语和葡萄牙语。欢迎大家试用，尤其想听听：结果说明是否容易理解、配置引导有没有遗漏，以及哪些措辞可能让人误以为“检查通过就代表安全”。
