### 【文章自荐】为什么有人说 Python 的多线程是鸡肋？我们是否错怪了它？ 👤 rockswang
> 文章在此： 标题：为什么有人说 Python 的多线程是鸡肋？我们是否错怪了它？ 在 Python 圈子里，“多线程是鸡肋”几乎成了一个“正确”的废话。不管是刚入门的新手，还是写了几年脚本的老鸟，只要遇到性能瓶颈，第一反应往往是：“害，Python 有 GIL（全局解释器锁），多线程是假的，换 Go 或者 Rust 吧。” 但事实真的如此吗？我想从认知偏差、门槛痛点以及实际收益三个维度，聊聊为什么 Python 多线程背了这么多年的“黑锅”。 1. 基因决定论：非科班工程师的“认知断层” Python 是一门极其成功的“跨界”语言。它的用户不只是软件工程专业的学生，还有大量的自动化运维、数据分析师、科研人员甚至财务人员。 这就是第一个痛点：认知断层。 对于很多非科班的开发者来说，他们写了几年的脚本，代码逻辑一直是“顺序执行”的。在他们的世界里，代码是 A 做完再做 B。当他们面临成千上万个任务需要加速时，突然被抛出一堆“异步、同步、阻塞、非阻塞、进程、线程、协程”的术语，这无异于降维打击。 由于缺乏底层并发模型的训练，很多人连“什么是线程安全”都还没搞清楚，就在多线程里写全局变量导致结果乱序，最后得出结论：“Python 多线程真难用，还是单线程稳当。” 2. 被误解的 GIL：IO 场景下的“真香定律” 大家谈 GIL 色变，主要是因为它限制了多核 CPU 的并行计算。确实，如果你在做大规模矩阵运算，多线程确实是鸡肋，你应该去用多进程或 NumPy。 但在现实世界中，90% 的脚本和工具都是 IO 密集型的： 请求网页 API 读写数据库 下载图片 读写本地文件 在这些场景下，CPU 大部分时间都在等网络返回、等磁盘响应。此时 GIL 根本不是瓶颈，线程切换的开销也微乎其微。 很多人宁愿忍受单线程慢速运行，或者花大量时间去重构到别的语言，也不愿（或不会）在 Python 里开启多线程。这导致 Python 多线程的实际运用率低得可怜，进一步加剧了“多线程无用”的刻板印象。 3. 门槛痛点：被“过度设计”的标准库 API 即便开发者想要尝试并发，Python 自带的 threading 或 concurrent.futures 库也并不够友好。 我们来看看官方推荐的 ThreadPoolExecutor： 你需要理解什么是 Executor。 你需要管理 Future 对象。 你需要处理 callback 或者用 ascompleted 来获取结果。 对于只想快速写个爬虫、或者批量调一下 API 的工程师来说，这些概念显得太“重”了。他们需要的其实很简单：“我有一堆任务，你帮我并发跑一下，告诉我什么时候完事。” 这种“想要个锤子，你却给了我一个五金店”的挫败感，让很多人在尝试阶段就退缩了，从而转去寻找其他看起来“更原生支持并发”的语言。 如何“无痛”升级你的代码效率？ 我曾经也深受其扰。我想要的是一种 “傻瓜式” 的升级体验：我的逻辑已经写好了，能不能改两行代码，就让它从“一个接一个跑”变成“一堆一起跑”？ 在尝试了各种封装库都觉得太重之后，我自己动手写了一个极简的工具：litetaskman。 它的核心逻辑非常纯粹，就是为了解决上述痛点： 1. 无痛升级：你不需要懂什么是 Future，不需要手写循环去检查任务状态。它能直接把耗时从 sum(cost)（总和）压缩到 max(cost)（最大值）。 2. 支持“边跑边加”：很多场景（比如爬虫）在开始前并不知道有多少任务，litetaskman 允许你在执行过程中动态添加任务，充分利用线程池。 3. 极致轻量：整个项目只有 100 行代码。这意味着你甚至可以直接把这 100 行拷进你的项目里，没有任何冗余依赖。 演示 我们用 “准备一顿丰盛早餐” 来做个对比。假设你有三个任务：打豆浆、买包子、包饺子。 过去：苦哈哈的“顺序逻辑” 代码必须等豆浆机转完，你才能出门买包子；买完包子回来，才能开始包饺子。 python 假设每个函数都是耗时的 IO 或等待任务 总执行时间 = 打豆浆(3s) + 买包子(5s) + 包饺子(4s) = 12s soymilk = makesoymilk(soy, milk) buns = buybuns(2) dumplings = makedumplings(8, type='pork') print("早餐准备好了！") 现在：极简的“并发逻辑” (使用 litetaskman) 你只需要简单增加三行，把函数和参数丢给 TaskMan，让它帮你同时调度。 python from litetaskman import TaskMan 1. 创建任务管理者（默认线程池） tman = TaskMan() 2. 添加任务：原函数名作为第一个参数，后续参数原封不动 tman.add(makesoymilk, soy, milk) tman.add(buybuns, 2) tman.add(makedumplings, 8, type='pork') 3. 执行并等待。结果顺序严格对应 add 的顺序，支持一气呵成拆包 总执行时间 = max(3s, 5s, 4s) = 5s soymilk, buns, dumplings = [r.result for r in tman.exec()] print(f"早餐准备好了！获得：{soymilk}, {buns}, {dumplings}") 为什么 litetaskman 值得一试？ 1. 无痛升级：如上所示，你的业务逻辑几乎不用改动，只是换了一种“提交”方式。 2. 效率质变：总耗时从 （累加）降低到 （耗时最长的那个任务）。 3. 边跑边加：它支持动态添加任务，特别适合爬虫这种“爬到一个链接再加一个任务”的场景。 4. 极其轻量：核心代码仅 100 行，没有任何臃肿的依赖。 总结 Python 的多线程不是鸡肋，它是被过高的门槛和被妖魔化的 GIL 束缚住的“利器”。 对于大多数开发者来说，我们不需要成为并发专家，我们只需要一个简单、直观、能解决 IO 等待问题的方案。不要因为工具复杂而放弃性能提升，也不要因为听信流言而放弃 Python 强大的生态。 有时候，轻量级，才是生产力。 项目地址： 你会因为 GIL 而放弃 Python 吗？欢迎在评论区分享你的看法。
