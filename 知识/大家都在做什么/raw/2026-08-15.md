### 【开源自荐】kvcached:让多个大模型弹性共享一张 GPU 的显存 👤 RixinLiu
> kvcached 是给 vLLM / SGLang 用的 KV cache 库,让多个模型共享一张 GPU 的显存。 一张 GPU 上想同时跑两个大模型,现在只能手动切显存，vLLM 的gpumemoryutilization 启动时就把显存占死,整晚没请求也不还,分多了 OOM,分少了浪费。 kvcached 把 KV cache 的虚拟地址和物理显存拆开:启动只预留地址空间,真有请求写 KV 时才映射物理显存,用完归还。相当于给 GPU 显存加了一层操作系统式的虚拟内存,谁用谁占。 一张 A10080G 跑 3 个 Llama3.18B,面对间歇峰值流量,首 token 延迟比静态切分低 2~28 倍。 不用改引擎代码: pip install kvcached nobuildisolation export ENABLEKVCACHED=true KVCACHEDAUTOPATCH=1 照常 vllm serve / sglang.launchserver 即可 支持 vLLM 和 SGLang,Apache 2.0。Red Hat 已基于它做了 K8s 上的多模型动态部署。

### 【开源自荐】MCP Lens：让 DeepSeek Harness 的 1,000 个 MCP 工具只占两个模型入口 👤 labmimors
> 【开源自荐】MCP Lens：让 DeepSeek Harness 的 1,000 个 MCP 工具只占两个模型入口 DeepSeek Harness 可以连接很多 MCP Server，但当目录增长到几百、上千个工具时，把所有工具 Schema 每轮都交给模型，会让请求变得很重。 MCP Lens 是一个 MIT 开源的 Harness 插件。它把远端目录放在本地可搜索目录后，只给模型两个稳定入口： mcpsearch(query)：找到候选工具，只返回命中项的准确 inputSchema mcpcall(server, tool, arguments)：调用明确选中的原始工具 在同一套 DeepSeek Harness 0.1.0rc.6、同一 1,000 工具 fixture、同样三个任务的 V4 Flash 实测中： 完整模型可见工具：1,025 → 27（双方共享 25 个非 MCP 工具，MCP 工具面实际为 1,000 → 2） request/header.tools JSON：674,249 B → 27,401 B，减少 95.936% 任务完成：3/3 → 3/3 按 20260814 抓取的价格估算：$0.0307204 → $0.0034707 代价也公开：Lens 多一次搜索步骤，这组任务的输出 Token 从 491 增到 794；这不是通用延迟或质量结论。 项目还提供了一个完全在浏览器本地运行的目录计算器。可以粘贴脱敏后的 MCP Tool JSON，查看自己的模型可见 Schema 数量和 UTF8 字节；内容不会上传。 GitHub： 本地目录计算器： 公开复现实验： Lens 对比图
