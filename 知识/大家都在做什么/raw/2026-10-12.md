### 【开源自荐】reasoning-router：让分类器为编程 Agent 的每一步选择推理强度 👤 robertn702
> 我一直把编程 Agent 的推理强度开在 high，连改名这种小事也是，用量消耗得很快。但降到 medium 又会出错：在一个较难的 pytest bug 上，GPT-6 Astra 用 medium 5 次只解决了 1 次。 所以我做了 reasoning-router。编程 Agent 每次请求模型之前，它先让一个小型分类器（默认是 TypeSafe 的 Jev，也可以换成 Cloudflare Clef、Laya 等）判断这一步需要多少推理强度，再把结果加到请求里。 切换推理强度通常会让 prompt cache 失效。它用 OpenAI 的 configurationupdate 和 Anthropic 的对话中 effort 消息来改强度，之前的上下文不变，所以缓存还能命中。 在 10 个 SWE-bench Verified 问题上，路由和固定 high 都解决了 44/44，路由少用约 14% 的输出 token，耗时少约 9%。只测了一个模型和一组任务，结果仅供参考。 支持 OpenCode 插件、Pi 扩展，以及可接入 Codex CLI 的本地代理。目前是 alpha 版本，MIT 协议。

### 【开源自荐】麦麦点餐最优解 - 用 Python 算清麦当劳优惠券的开源 Skill 👤 minxin88
> 一个跑在 WorkBuddy 上的开源 Skill：接麦当劳中国官方 MCP，拉门店真实菜单、真实营养数据、真实可用优惠券，再用本地 Python 脚本穷举所有搭配，算出「最省 / 最健康 / 性价比最高」三套能直接下单的方案。 它只依赖 Python 标准库，不需要 pip install，也不需要 MCP Token 就能先跑一遍离线示例看效果。 为什么做这个项目？ 麦当劳的优惠券是满减、折扣、品类限定混着来的，单看每一张都懂，放在一起就不会算了。 举个真实的坑：手里有「满 40 减 10」和「汉堡 8.8 折」两张券。 买一个 25.5 元的汉堡：8.8 折省 3.06 元，满减用不了 → 折扣赢 买两个（51 元）：8.8 折省 6.12 元，满减省 10 元 → 满减赢 再加一份 12 元薯条凑到 63 元：薯条白买了 —— 券已经封顶在减 10，多花的 12 元一分没省 也就是说，哪张券最省、要不要凑单，完全取决于你这单的构成，没有标准答案。 再叠上「预算 45 元、热量不超 1100 kcal、蛋白质要 35 克以上」这类约束，满足条件的组合轻松上千套，人手不可能算完。 它是怎么工作的？ 核心设计是把「算」和「说」分开： 用户说人话 │ "两个人吃、50 块以内、别太油" ▼ 大模型理解意图 ──► 翻译成硬约束（预算/热量/蛋白质/忌口） │ ▼ 麦当劳 MCP 拉真实数据 ──► 门店菜单 / 营养 / 可用券 │ ▼ 本地 Python 脚本（无网络）──► 穷举全部组合 + 券最优匹配 │ ▼ 大模型组织成人话 ──► 三套方案 为什么不把枚举交给大模型？ 上千套组合的枚举是纯数学问题，不是语言问题。交给大模型：慢、贵、会算错钱；交给脚本：几毫秒出结果、可复现、零 token 消耗。 功能与特点 真实数据：菜单、价格、营养、优惠券全部来自麦当劳官方 MCP 实时接口，不内置任何硬编码数据表 券最优匹配：对每个组合遍历所有券，按「这一单实际能减多少」挑最省的那张（一张订单只能用一张券，不能简单挑面额大的） 三种口味排序：最省（实付升序）/ 最健康（热量蛋白质偏离度）/ 性价比（每 1 元换到的蛋白质克数） 零依赖：Python 3.9+，只用标准库，无网络请求 先试后配：内置离线示例数据，python scripts/optimizemeal.py --demo 无需 Token 即可跑出结果 有边界：不主动下单、不自动领券；涉及花钱的操作一律先让用户确认门店、取餐方式和商品清单 实测 2026-10-12 在深圳北站站内一店（早餐时段）真实跑过一次：约束为预算 ≤ 45 元、热量 ≤ 1100 kcal、蛋白质 ≥ 35 g，共枚举出 127 套可行组合，最省方案实付 29.4 元。

### Toolmaker Agent: 一个基于智能体的 SDLC 平台，支持人类与智能体在同一结构化数据模型上开展协作。 👤 rts-gordon
> 当 AI 开始写代码，如何管理好你的产品需求和设计？ 让人、产品和编码智能体，共用一份不会散落的项目长期记忆。 这两年，团队写代码和文档的速度变快了。 开一场会，AI 能帮你生成会议纪要；使用 Superpower skills 讨论一个功能，几分钟就能得到一份 spec；让 Claude Code、Codex 或其他编码智能体开始工作，又会多出 plan、ADR、实现说明和测试记录。 看起来，每个人都更高效了。 但项目并没有因此更容易管理。相反，很多团队正在经历另一种混乱：文档散落在不同目录、不同仓库、不同聊天记录里。产品经理记得当初的目标，开发记得实现时的取舍，AI 记得当前上下文——可当需要回答“这个需求是谁定的？”、“它属于哪个特性？”、“哪些设计图和它有关？”时，大家又回到了搜索 Markdown、翻聊天记录和开会确认。 问题从来不是少了一份文档，而是缺少一个能让结论持续存在、可被查询和复用的地方。 Toolmaker Agent 正是为这件事而来。 1. 软件工程在 AI 时代的回归 AI 把写代码、写说明和生成方案的速度提升到了新的量级，但它没有消除软件工程要解决的核心问题：目标是否清楚、边界是否一致、决策能否追溯、变更是否可控，以及不同角色能否基于同一份事实协作。恰恰因为产出更快、参与者更多，这些问题比过去更容易被放大。 过去一段时间，团队往往把注意力放在“让 AI 再生成一份内容”上，而忽视了软件工程最基础的工作：把已确认的结论组织成可管理、可复用、可验证的资产。没有这层基础，AI 生成的 spec、plan 和代码会更快地累积，也会更快地失去上下文。 Toolmaker Agent 按照软件工程的标准设计和开发：用 Product、Feature、Requirement 与 UML 表达边界和关系，用稳定 OID、修订版本与关联关系保留演进过程，并通过网页、对话和 MCP 让同一份项目事实服务于人和智能体。这不是回到笨重的流程，而是在 AI 加速交付时，让软件工程重新成为团队共同的工作底座。 2. 不把 AI 产出再丢进一个文件夹 Toolmaker Agent 是一个面向 AI SDLC 的本地工作台。它把产品（Product）、特性（Feature）、需求（Requirement）和 UML/4+1 系统设计图，放进同一套结构化数据模型里。 这意味着，一条需求不再只是某份 Markdown 里的段落：它有稳定的 OID、有父子关系、有修订版本，也能和所在特性、产品和系统设计图关联起来。无论是产品负责人梳理范围，还是技术负责人回溯设计决策，面对的都是同一份项目事实，而不是各自手里的“最新版”。 更重要的是，这份事实不只给人看，也可以给智能体用。 3. 一套数据，三种工作方式 不同角色不必被迫使用同一种界面。Toolmaker Agent 为同一份数据提供了三种入口。 3.1 产品和研发可以在网页里直接管理。 像使用普通工作台一样创建 Product、Feature、Requirement 和 UML 图；系统设计图使用 Mermaid 渲染，并可导出 PNG 或 SVG。该手动模式不依赖 AI，是最直接、最可控的基础能力。 3.2 也可以和 AI 对话，把讨论变成结构化结论。 例如，你可以先和对话智能体讨论请假流程里的审批边界、例外情况和优先级。结论收敛后，再让它整理成一个 Feature 和多条 Requirement。 这里有一个值得强调的设计：在网页对话中，每一次写入都会先进入“提议 → 确认”流程。模型会把准备创建或修改的字段列出来；在你点击确认之前，数据不会落库。AI 可以帮你组织和补全信息，但最终决定权仍然在你手里。 演示动画：LLM Chat交流 3.3 编码智能体则可以通过 MCP 直接接入。 把 Toolmaker Agent 注册到 Claude Code、Codex 或 DeepSeek Harness 后，智能体便能在终端中查询、创建、更新和删除同一份 Product、Feature、Requirement 与 UML 数据。一次方案讨论结束后，不必再手工把结论搬运到另一个系统：让智能体调用 MCP 工具，即可把它保存为后续任何人、任何智能体都能查询的项目资产。 网页、对话和 MCP 背后是同一个 service 层和同一份数据库。换句话说，产品经理在网页里创建的需求，开发可以在终端中查询；编码智能体补充的设计记录，团队也能在网页中继续完善。 演示动画：MCP 操作 4.
