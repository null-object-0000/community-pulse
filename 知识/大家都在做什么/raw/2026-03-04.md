### 【开源自荐】ESPClaw — 嵌入式领域的 OpenClaw，最便宜的 AI Agent 学习平台 👤 tianrking
> 项目地址 ESPClaw 是什么 嵌入式领域的 OpenClaw，最便宜的嵌入式 AI Agent 学习平台。一个能在 2 美元芯片上跑的 AI Agent 固件，纯 C 实现，4MB Flash 就够了。 我们想回答一个问题：Agent 的核心能力，能不能塞进最便宜的芯片里？ 演示视频 ESPClaw 想在这些探索上再往前走一步：如果砍掉 PSRAM，用最便宜的 C3，Agent 还能跑吗？ 能力位掩码，自动适配平台 同一个固件，C3 / C5 / S3 都能跑。Tool Registry 在启动时根据芯片能力自动过滤可用工具：C3/C5 用基础工具，S3 用全部工具。一套代码，三种芯片。 4. 安全护栏在 HAL 层 GPIO 操作不直接调用 ESPIDF API，而是走 HAL 层。HAL 层会检查引脚是否在允许范围内，不在就拒绝。安全不是靠"小心写代码"，而是靠架构设计。 5. ### 【工具推荐】：一个安全的OpenClaw skill技能市场：解决AI助手「只聊天不干活」的困境 👤 dafa6
> 【工具】我做了一个安全的OpenClaw技能市场：解决AI助手「只聊天不干活」的困境 相信很多朋友和我一样，第一次看到 OpenClaw 时是兴奋的——一个本地运行的 AI 助手，能帮你处理文件、执行命令、调用 API，这不就是我们想要的 Jarvis 吗？ 但实际用起来，事情好像没那么简单。 为什么你的AI助手「只会聊天不会干活」 OpenClaw 默认配置下，大多数用户（包括不少开发者）发现它最终还是退化成了一 个「聊天 + 文件助手」。不是它做不到更多，而是不知道能做什么、该装什么。 我观察了一段时间，发现问题主要出在三个方面： 第一，技能发现困难。 官方文档里只列出了基础能力，社群中不断有新的技能被开发出来，但信息散落在 Discord、GitHub Issue 和各种博客里，普通人根本追不过来。 第二，安装第三方技能有心理门槛。 说白了，技能本质上是一段可以执行命令、访问文件、调用 API 的代码。，这在开发者圈子里不算新鲜，但如果你看过最近几年 npm 仓库里的恶意包事件、PyPI 上的钓鱼攻击，就不会随随便便运行一个陌生人写的脚本。 第三，缺乏评估标准。 看到一个技能，我怎么知道它是谁写的？维护状态如何？权限范围多大？有没有历史安全漏洞？这些问题通常没有现成答案。 这些问题加在一起，OpenClaw 的体验就变成了：功能很强，但用不起来。 解决思路：构建一个安全优先的技能发现与评估体系 我花了些时间做了一个小项目，叫 OpenClaw Skills Directory 地址是（ OpenClaw 真正变成生产力工具，而不是一个高级点的聊天机器人。 <img width="567" height="269" alt="Image" src=" / <img width="567" height="319" alt="Image" src=" / 这个目录目前收录了官方和社区贡献的 OpenClaw 技能，按类别整理，并且会持续追踪更新。我自己在用的时候，最看重的其实是「信任体系」——所以我在目录里加了几个实用的小设计： 技能来源标注：区分官方维护和社区贡献，一目了然 权限说明：每个技能申请了哪些系统权限，部署前心里有底 更新状态：最近一次提交是什么时候，避免装一个已经无人维护的技能 安全采纳建议：代码审查、分环境测试、版本锁定——自动化流程也值得遵循「生产环境三板斧」 如果你正在用或者想用 OpenClaw，这个目录应该能帮你省掉不少「这个技能到底靠不靠谱」的纠结时间。 实测案例：我是如何用技能市场将OpenClaw变成自动化管家的 我自己目前的用法是这样的： 每天早上，OpenClaw 会根据我预设的技能组合，自动抓取几 个数据源的更新、生成摘要、推送到我的消息软件。整个过程不需要我手动触发，它「知道」该在什么场景用什么技能。 这个过程听起来简单，但关键在于：技能是可控的、权限是透明的、出了问题是可以回滚的。这也是我做这个目录的初心——不是让大家盲目装很多酷炫的技能，而是让你装得明白、用得放心。 欢迎参与：你在安装第三方技能时最看重哪些信任要素？ 写这篇推荐的同时，我也想听听大家的想法： 维护者身份公开重要吗？ 权限差异（diff）展示有没有帮助？ 可复现的安装步骤、签名发布，这些信任信号会让你安装得更果断吗？ 欢迎在评论区聊聊你的想法，这个目录我会持续维护下去，也欢迎社区里的技能作者提交自己的作品。 探索一下： 如果有任何问题或者想交流使用心得，随时找我。祝大家把 OpenClaw 真正用起来！
