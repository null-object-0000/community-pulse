### 【开源自荐】Fuwa：一个 macOS 窗口置顶工具 👤 yuxino
> 我以前就想要一个这样的工具。做微信小程序时，一边改代码，一边想看开发者工具里的预览；做 App 时要盯着模拟器检查布局。编辑器一盖住这些窗口，就得反复切回来。跟着视频教程操作也一样：看一步、切回软件做一步，再切回去找刚才讲到哪儿。对照设计稿调界面，或照着 PDF 文档填参数时，也会碰到这个问题。 最近借助 AI，总算把这个想法写成了 Fuwa。做完才发现市面上已经有同类工具了，不过这个是我自己做的版本，用下来觉得挺顺手，就开源分享给大家。 Fuwa 是一个 macOS 窗口置顶工具。把想看的窗口切到前面，按 ⌥⌘P，它会在最上层显示这个窗口的实时画面。回到编辑器或正在操作的软件，预览、教程、设计稿还在眼前；置顶画面会让鼠标点击穿过去，不挡住下面的工作。也可以同时固定几个窗口，或者冻结画面，方便对着某一步慢慢做。需要操作原窗口时，可以用“显示源窗口”切回去。 Fuwa 支持 macOS 14 及以上。首次固定窗口时需要屏幕录制权限；窗口画面只在本机处理，不上传。

### 【网站自荐】SupaQR：把二维码、短链接和文件分享整合到一起的在线工具 👤 cenaczx
> 【网站自荐】SupaQR：一个把二维码、短链接和文件分享放在一起的在线工具 大家好，向大家自荐一个我自己开发的产品 SupaQR： SupaQR 是一个集 二维码生成、短链接、文件分享和访问统计 于一体的在线工具。 最开始它只是一个二维码生成器，后来随着自己不断使用，我发现二维码背后真正需要解决的问题，往往并不只是“生成一张二维码图片”。 比如： 印刷出去的二维码，目标链接以后可能需要修改 想知道二维码到底有没有人扫、什么时候扫、从哪里扫 想把 PDF、图片、音频等文件直接变成二维码 营销活动需要批量生成二维码 一个很长的网址，希望变成容易传播的短链接 文件发给客户以后，希望知道有没有被打开 希望二维码和短链接都能使用自己的品牌域名 这些需求通常需要几个不同的工具才能完成。 所以我慢慢把 SupaQR 做成了现在这个样子，希望尽量用一个产品解决从： 二维码 / 短链接 → 分享 → 访问 → 数据统计 这一整套流程。 为什么开发 SupaQR？ 市面上其实已经有很多优秀的二维码和短链接产品。 但我自己使用这些产品时，一直有两个比较明显的感受。 第一个是功能比较分散。 二维码生成、URL Shortener、文件分享、访问统计，经常分别属于不同的产品。 第二个是很多二维码工具的定价并不便宜。 尤其是动态二维码。 二维码一旦印在包装、宣传册、名片或者线下物料上，重新印刷的成本其实远远高于二维码本身。 所以我希望 SupaQR 能做成一个： 功能足够完整，但价格尽量简单、便宜，而且普通人不需要研究半天就能使用的工具。 目前可以做什么？ 1. 动态二维码 可以创建动态二维码。 二维码印刷以后，即使目标网址发生变化，也可以直接修改二维码背后的目标内容，不需要重新生成和印刷二维码。 同时可以查看二维码的扫描数据。 2. 自定义二维码样式 支持修改： 颜色 Pattern Eye 样式 Frame Logo 生成以后可以下载 PNG、JPG、SVG、EPS 等格式。 所以除了网页使用，也比较适合包装、海报、宣传册等需要高清打印的场景。 3. 多种二维码类型 除了普通网址二维码，目前还可以创建包括： URL File Document vCard Page Form Menu App Store Image Audio Video 等不同类型的二维码。 4. 短链接 SupaQR 同时也是一个 URL Shortener。 可以： 创建短链接 自定义短链接后缀 使用自己的域名 查看点击统计 设置链接过期时间 批量创建链接 这样二维码和短链接的数据可以放在同一个后台管理。 5. 文件分享 可以直接上传： 图片 PDF Word Excel PPT 视频 音频 Markdown 3D 文件 等文件。 上传以后可以生成分享链接或者二维码。 同时支持密码、过期时间、下载限制和访问统计等功能。 所以有时候甚至不需要自己先找地方托管 PDF，再生成二维码。 6. 数据统计 动态二维码和短链接都可以记录访问数据。 对于线下宣传来说，我觉得这个功能比较有价值。 因为以前印一张传单或者贴一个海报，基本不知道到底有没有人看。 换成动态二维码以后，至少可以知道： 这张二维码有没有人扫描。 也可以进一步分析不同二维码、不同渠道和不同线下位置带来的访问效果。 7. API SupaQR 也提供 API： 如果需要批量生成二维码或者把二维码、短链接能力接入自己的系统，可以直接通过 API 完成。 免费版 SupaQR 有免费版本，不需要信用卡。 目前免费计划可以创建动态二维码、静态二维码和短链接，并且二维码扫描次数不限。 对于个人项目、小网站或者只是偶尔需要制作二维码的人，免费版本基本就可以直接开始使用。 我比较想做的一件事 我不太希望 SupaQR 最后只是变成一个： “输入网址 → 下载二维码” 的工具。 我更希望二维码成为连接现实世界和网页服务的一个入口。 比如一家餐厅贴出的二维码，背后不只是一个 PDF； 一家维修公司的车辆上贴出的二维码，背后也不一定只是官方网站； 展会、产品包装、门店、设备、名片等线下场景，其实都可以通过二维码连接到不同的网页应用和后续操作。 所以我现在也在继续尝试，让 SupaQR 从单纯的 QR Code Generator，慢慢变成： Scan → Action → Track 即： 扫码 → 完成操作 → 记录结果 而不仅仅是“扫完跳到一个网址”。 这个方向目前还在持续开发。 一些适合 SupaQR 的场景 目前我觉得比较典型的场景包括： 餐厅菜单二维码 产品包装二维码 PDF / 产品手册二维码 展会宣传二维码 名片 / vCard Wi-Fi 二维码 App 下载二维码 音频导览 活动二维码 短链接营销 文件分享 印刷品访问统计 如果你的二维码以后可能修改内容，建议使用动态二维码； 如果内容永远不会变化，用静态二维码就足够了。 最后 这是一个还在持续开发中的产品。

### 【开源自荐】seiso：给 AI 写的项目文档做 lint，查出对话残留、过时版本号和失效链接 👤 scarletkc
> 现在项目里的 Markdown 文档越来越多是 AI 写的，写的速度远远快过人审的速度。更麻烦的是，Claude Code、Codex 这类 coding agent 在下一次改代码时，又会把这些文档当成上下文读回去。文档里一个过时的版本号，或者一份字段列表在三处副本里只改了一处，人会被误导，agent 也会照着错的继续改。而且 AI 写文档，翻来覆去犯的就是那几种错。 seiso 是一套项目文档的 Markdown 约定，加上按这套约定做检查的 linter，用 Rust 写的。思路类似 rustfmt 统一了 Rust 的代码格式，各个项目共用同一套规则，不用每家自己重新商量。项目要做的主要是把自己的文档对应到类型上，seiso init 会给出一份初始配置。 约定的核心是这几条。 每篇文档声明一种类型，比如 howto、reference、adr，只写这种类型该写的内容。操作指南只给步骤，为什么这样设计放进 ADR。 每个事实只有一个归属页面，其他页面链接过去，不再复述一遍。 长期存在的页面不记录比页面本身变得更快的值，比如版本号、部署状态和数量。 成稿不对提需求的人说话，也不交代自己是怎么写出来的。 工具判断不了的例外要写明理由，没写理由的例外本身就算违规。 下面是对一篇中文部署文档的实际检查结果： text $ seiso check --preview docs/deploy.md:7:7: VOX001 This phrase refers to the requester of an earlier conversation. | 7 | 好的，下面是按你的要求更新后的部署指南。 | = suggestion: State the document's instructions or facts directly for its readers. docs/deploy.md:9:12: STL001 This sentence pairs a current-state marker with a value that can change. | 9 | 当前生产环境运行的是 2.3.1 版本。 | = suggestion: Link to the source that owns the value, or state a lasting requirement with its constraint. docs/deploy.md:14:5: LNK001 Local link target "config.md" does not exist in the workspace. | 14 | 配置项见配置说明。 | = suggestion: Update the path or restore the target; paths resolve from this document's directory, or from the workspace root when they start with /, and seiso does not add .md or index.md. Found 3 diagnostics. 每条诊断都会给出位置和修改建议，agent 只看 seiso 的输出就能修掉大部分问题。遇到需要人来判断的情况，比如两个页面到底哪个拥有某个事实，诊断会直接点出要做的决定。seiso 不去猜一段话像不像机器写的，格式和拼写也留给其他工具。 我对误报比较保守。新规则一律先进 preview，要在固定版本的真实仓库语料上攒够至少 100 条逐条人工复核的留出集诊断，精度达到 95% 以上，才会升级成默认启用的稳定规则。所以现在默认只跑文档类型声明、本地链接目标和抑制注释这几条稳定规则，上面例子里的对话残留和当前状态值检查还在 preview，要加 --preview 才会开启。宁可漏报，也不给没有依据的诊断。 它可以接进 Claude Code 的 PostToolUse hook。agent 每次用 Write 或 Edit 改完一个 Markdown 文件，seiso 就检查这个文件，发现问题时用退出码 2 把诊断直接反馈给 Claude，让它当场修掉。另外也支持 pre-commit 和 CI。中文、英文和日文文档都能检查。 sh 三种安装方式任选一种 cargo install seiso uv tool install seiso # 或 pipx install seiso npm install -g @scarletkc/seiso 在仓库根目录 seiso init seiso check PyPI 和 npm 包自带主流平台的预编译二进制，不需要装 Rust 工具链。MIT 协议。
