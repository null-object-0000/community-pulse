### 〖开源自荐〗shajara：把 JavaScript 异步工作放进 scope tree 的结构化并发库 👤 iplaylf2
> 项目简介 大家好，我做了 shajara，一个 JavaScript/TypeScript 的结构化并发库。 它不是 Promise 的替代品，而是给 Promise、回调、定时器、fetch(...)、WebSocket 等异步工作补上一层生命周期结构。 很多异步代码的问题不在“怎么 await 一个结果”，而在旁边那些被启动的工作没人说得清： 它属于哪个请求、页面、面板或任务？ 父流程失败时，它该不该被取消？ 回调晚到时，还能不能写入结果？ 外部资源应该什么时候清理？ shajara 关注的不是把异步调用写短，而是让异步工作有明确归属和可预期的收尾。 核心模型 shajara 用 JavaScript generator function 写 routine，用 yield 标出 routine 把控制交给运行时的位置。运行时会把工作放进一棵 scope tree： spawn(...) 在当前 scope 里启动 process。 branch(...) 创建 child scope。 future、channel、resource、AbortSignal 等句柄，都由创建它们的 scope 拥有。 scope 收敛时，会先收拢自己拥有的 child scope、process 和句柄，再把最终结果交给等待方。 一个例子 ts import { run, sleep } from "@shajara/host"; import { branch, spawn } from "@shajara/host/primitives"; const result = await run(function saveProfile() { return yield branch(function saveProfileScope() { yield spawn(function writeAuditTrail() { yield sleep(30); return "audit written"; }); yield sleep(5); return "profile saved"; }); // writeAuditTrail 结束后，才得到 "profile saved"。 }); 这里 saveProfileScope 这段入口 routine 很快就返回了，但 branch(...) 等待的是整个 child scope，不只是这一个 function 的返回值。因为 writeAuditTrail 也是这个 child scope 拥有的 process，所以调用方会在它结束后才拿到 "profile saved"。这就是 shajara 文档里说的结构化收敛：调用方不用手动追踪 child scope 里每个后台任务，scope 会把自己拥有的工作收拢到一个结果边界。 失败与取消 失败和取消也沿着同一套结构处理。如果 child scope 中某个 process 抛错，这个 scope 会先取消自己拥有的其余工作，再让调用方在 branch(...) 的位置收到 ScopeError。如果某段后台工作失败后不应该影响同一个 scope 里的其他工作，就在这个 process 边界内把错误转换成普通结果，而不是等到外层 wait(...) 再补救。 和现有异步代码的关系 它和现有 Promise/回调代码的关系更像“把异步边界放回结构里”： until(...) 把已有 Promise 带入 routine 控制流。 all(...) / race(...) 表达常见并发组合，其中 race(...) 会在返回胜出值前取消未胜出的 routine。 completer(...) 和 feed(...) 分别把回调的一次结果和连续事件桥接成 future/channel。 abortSignal(...) 把原生 fetch(...) 这类 API 的取消绑定到当前 scope。 resource(...) 让 WebSocket 等外部资源在就绪后继续附着到所属 scope，并在 scope 释放时运行清理逻辑。 文档与演示 项目文档站有中文和英文文档，不只是 API 列表。文档按 Guides、Topics、Concepts 三层组织：先教怎么把 Promise、scope、外部句柄放进 routine，再解释 future、channel、context、recovery，最后展开 scope tree、句柄归属和 scope 退出语义。站内还有 Flow Explorer，可以用流程图回放 single spawn、future 完成、scope 拥有的工作、fork/join、失败触发取消、恢复边界、有界 channel 等场景。 链接 项目地址：github.com/iplaylf2/shajara 文档地址：iplaylf2.github.io/shajara NPM：@shajara/host

### 【开源自荐】ArgusMind：让 AI 像安全工程师一样做代码审计，自动发现 Sink 并追踪调用链 👤 pulseio76
> 项目地址： 在线预览： ArgusMind 是一个开源的 AI 代码安全审计 Agent。 它不是把代码丢给大模型，然后问一句“这里有没有漏洞”。它会像安全工程师一样，先理解项目结构，再制定审计计划，寻找危险 Sink，最后顺着调用链往上追，尝试还原一条风险路径。 我做这个项目，是因为现在很多 AI 工具都在帮人写代码，但很少有工具能像安全工程师一样系统地审代码。真实的代码审计不是一次问答，而是一连串判断：哪些模块值得看？哪些函数可能是危险点？参数是怎么传进来的？有没有可利用路径？ ArgusMind 尝试把这个过程拆成多个 Agent 协作完成： ProjectInfo Agent：理解项目语言、框架、入口和目录结构。 Plan Agent：根据项目信息生成审计计划，而不是盲扫整个仓库。 SinkFinder Agent：寻找危险函数、敏感 API 和潜在风险点。 ChainAnalyzer Agent：沿着调用链追踪数据流，分析风险路径是否成立。 和普通扫描器相比，我更希望 ArgusMind 做到的是：不只是告诉你“这里可能有问题”，而是告诉你“它是怎么一路追到这里的”。 所以项目里引入了 Neo4j，把语言、风险类型、Sink、调用链、分析结果都保存成审计图谱。审计结束后，可以在 Web 控制台里查看任务进度、漏洞详情和调用链图。 目前支持： 多 Agent 协作式代码审计 自动生成审计计划 自动发现危险 Sink 调用链追踪与风险路径分析 Neo4j 审计图谱 Web 控制台查看任务、漏洞和链路图 任务暂停、恢复、取消 Docker 本地部署 通过 LiteLLM 接入不同大模型 技术栈：Python / FastAPI / Neo4j / PostgreSQL / LiteLLM / Ant Design Pro。 欢迎对 AI 安全、代码审计、多 Agent、DevSecOps 感兴趣的同学试用和提建议。 <p align="center" alt="登录页" width="48%" / &nbsp; alt="控制台" width="48%" / </p <p align="center"<sub登录 · 控制台（Dashboard）</sub</p <p align="center" alt="项目管理" width="48%" / &nbsp; alt="任务管理" width="48%" / </p <p align="center"<sub项目管理 · 任务管理</sub</p <p align="center" alt="任务详情 代码审计链路图" width="96%" / </p <p align="center"<sub任务详情 · 代码审计链路图</sub</p <p align="center" alt="任务详情" width="48%" / &nbsp; alt="漏洞管理" width="48%" / </p <p align="center"<sub任务详情 · 漏洞管理</sub</p <p align="center" alt="漏洞详情" width="48%" / &nbsp; alt="漏洞详情" width="48%" / </p <p align="center"<sub漏洞详情（报告与代码审计链路图）</sub</p
