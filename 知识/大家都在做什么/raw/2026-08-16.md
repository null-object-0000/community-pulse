### 【开源自荐】kuaishuo（快说）：本地语音输入法 + 会议逐字稿 👤 MaskerPRC
> 打字慢的人大概都想过用语音输入，但市面上的方案要么每次要手动点"开始录音"、识别完还得复制粘贴，要么音频要过一遍云服务器——密码、薪资、病历全过了一遍别人的服务器。 快说想解决的是：开着就行，想输入的时候直接说，文字自动落到你正在打字的地方。全程本地，音频不出这台机器。 核心能力 挂着就行，不用每次启动 — 悬浮条常驻，不抢焦点。想输入时鼠标点进输入框直接说，不需要先去按一个"开始" 文字直接进光标 — 剪贴板 + 一次真实的 Ctrl+V，走真实粘贴路径。微信、飞书、VS Code、浏览器地址栏，任何地方。Draft.js / Lexical / TipTap 这类自维护文档模型的编辑器也不会错乱 声纹过滤，只认你的声音 — 电视、视频、旁边同事说话麦克风全听得见，能量和频谱分不出人（实测几乎完全重叠），声纹向量可以。录 3 段各 3 秒取平均，之后只有你的声音能驱动输入 全程本地 — SenseVoiceSmall 在本机跑，音频不出这台机器 会议逐字稿 — 只记不输入。额外录一路系统声音补上远程会议对方的发言，用声纹区分说话人。每识别出一句实时 POST 到你的接口（1~3 秒内到），会议结束再推完整稿 装完即用 — 识别模型（228MB）和声纹模型（27MB）内置在安装包里，不用首次启动等下载 不丢 — 每句话在识别出来的瞬间就 append 落盘（JSONL），崩溃、强杀、断电最多丢正在写的那一行 三种开始方式 按住说（Ctrl+Shift+Space）— 按住、说、松手。快按一下只听一句 一直录（Ctrl+Shift+D）— 按一次开始再按一次停，口述一整段用这个 会议（Ctrl+Shift+M）— 只记逐字稿，一个字都不输入到任何应用 技术栈与实现 Electron + Vue，识别用 SenseVoiceSmall，声纹用 sherpaonnx。198 个单测 + 43 项功能端到端 + 103 项 UI 端到端。 几个实现上的选择： VAD 放渲染进程——断句要看实时音频，渲染层为了画波形本来就拿着每一帧 系统声音是独立的第二路 VAD 而非混流——避免视频持续声音抬底噪导致麦克风一路不断句 实时推送敢丢（秒级有界重试），因为逐字稿已落盘、会议结束会整份重推 安装 下载最新 Release 安装包即可，模型内置。从源码跑： npm install npm run dev 项目链接 MIT 协议，Windows 平台。项目还在早期，欢迎试用和提 issue。

### 【开源自荐】app-safe：AI 代码安全自对抗演练场 👤 MaskerPRC
> 用 AI 写代码已经很普遍了，但 AI 写的代码到底有多少安全漏洞？这些漏洞有没有规律可循？能不能沉淀成一套可复用的安全测试提示词？ appsafe 就是为了回答这个问题做的。它让两个 Claude Code 线程互为对手，自动进行"写代码 → 攻代码 → 修漏洞 → 再攻击"的循环对抗，把 AI 代码中暴露出的安全漏洞逐个记录、归纳，最终沉淀成一个安全测试 prompt 库。 核心设计 Builder（建造者）：像普通人用 AI 快速写业务代码一样，自然地写、加功能、迭代。不做刻意安全加固，让漏洞自然暴露。收到攻击报告后才针对性修复。 Attacker（攻击者）：黑盒安全测试者，只能读接口文档 + 打运行中的服务，禁止读源码。完全模拟"外部攻击者只拿到 API"的真实场景。 文件系统握手：双方不直接对话，通过 arena/ 目录下的文件交换信息——接口清单、攻击报告、漏洞知识库、轮次状态。 漏洞知识库：每个被证实的漏洞记录为一个 VULNXXX.md，包含漏洞类型、严重级别、复现步骤、影响评估，以及最重要的——一段可复用的安全测试提示词（attackprompt），让任何测试者都能用同样的思路命中这类问题。 一轮怎么走 1. Builder 构建/迭代应用，发布接口文档 → 2. Attacker 读接口文档，对运行中的服务做端到端攻击，写攻击报告 + 漏洞记录 → 3. Builder 读报告，修复漏洞，迭代到下一轮 → 4. 循环往复，直到某一轮 Attacker 找不到漏洞或达到约定轮数 为什么有意思 自动化红蓝对抗：不需要组织人来打 CTF，两个 AI 线程自己就能跑攻防循环 真正的黑盒：Attacker 完全看不到源码，复现真实攻击场景 产出可复用：每轮发现的漏洞都抽象成测试提示词，积累下来就是一份 AI 代码安全测试清单 观察 AI 修漏洞能力：Builder 修复后 Attacker 再攻击，能观察 AI 是否真正修好了、还是引入了新问题 技术栈 Node.js 应用，目标服务跑在 项目链接 如果你也在关注 AI 代码安全问题，欢迎试用和提 issue。

### 【开源自荐】volens：一个能让你 “平时用不上、排障离不开” 的 GPU 省钱利器 👤 sceneryback
> AI 集群里的 Pending，为什么特别难排查 AI 训练和推理基本离不开 GPU、NPU 等计算卡。和普通业务集群相比，这类环境通常同时具备几个特点。 1. 多团队竞争昂贵资源 算法、训练、推理和评测团队共享同一批卡，队列、优先级、配额、抢占和 Gang Scheduling 交织在一起。最让人困惑的情况不是“集群真的没资源”，而是：看着资源够，任务就是排不上队。节点上可能有空闲卡，但队列已经没有可用额度；队列还有额度，但单个节点放不下整个 Pod；某个已经 Inqueue、却永远无法分配的 PodGroup，又可能继续占着队列资源。 2. Volcano 有自己的调度语义 AI 场景广泛使用 Volcano。它不是简单地把 Pod 交给 Kubernetes 默认调度器，而是按照自己的调度链路执行：先判断 PodGroup 能否入队，再执行 JobValid，最后进入节点分配和各插件过滤。proportion、capacity、gang、predicates、deviceshare，以及厂商提供的 GPU/NPU 插件，都可能影响最终结果。算法研发同学通常不熟悉这些机制；集群运维同学也很难记住不同 Volcano 版本中每个插件的具体行为。 3. 大容量存储让调度条件更复杂 训练数据集和模型权重通常依赖大容量存储。PVC/PV 亲和性、Volume Zone、CSI Volume Limits、访问模式、StorageClass 和本地盘拓扑，都是常见故障来源。很多问题表面上是 Pod Pending，根因却可能是卷只能落在某个可用区、节点已达到 CSI 卷数量上限，或者 Pod 的节点约束和存储拓扑互相冲突。 4. 每一分钟故障都在花钱 GPU、NPU 通常按时间计费，而且价格不低。一个分布式任务缺少一个成员时，其他已经启动的 Pod 可能仍占着整机计算卡等待。排障每多花一分钟，都可能意味着一组昂贵资源在空转。 所以 Pending 排障不能只靠“经验好的人恰好在线”，更不能每次都从头执行一遍命令。工具化，才能真正节省时间和成本。 我做了一个 Volcano 排障工具：Volens Volens 是一个深度集成 Volcano 调度经验的 Pending Pod 诊断工具，已经在生产环境久经验证。它以 Pod 形式部署在 Kubernetes 集群中，通过 Web 页面选择故障 Pod，然后沿 Volcano 实际可达的调度顺序给出检查结果： 项目地址： 部分效果如图，欢迎体验 😁：
