# DevTrends 产品库与混合渲染规划

> 2026-09-14 讨论产出并开始实施。**状态：阶段 1 与趋势查询纵切已完成；日报投影、全量 LLM 回填与长尾 SSR 尚未切换。**
> 触发问题：「趋势洞察里的产品是抓取到的全量产品，还是每日日报里展示的展品？」
> 答案：是日报展示的展品（`scripts/build-site.js` 只把 `知识/大家都在做什么/raw/*.json` 喂给趋势模型，那是日报视图）。由此引出两层重构：**后加工与日报解耦（产品库）** 与 **核心静态 + 长尾服务端渲染（混合渲染）**。
> 关系：延伸 `docs/架构重构规划.md`（方案 A 渐进模块化）与 `docs/长期架构路线.md`（版本化 enhancement JSON / source-raw 外置）；**渲染部分推翻 `docs/架构方案.md` 的「不做 SSR」**，并提前 `docs/长期架构路线.md` 里「到 60000–70000 文件再验证长尾按需渲染」那条触发条件。

## 当前落地状态（2026-09-14）

第一批不是再生成一套大 JSON，而是把「证据、事实、内容、发布视图」拆成可迁移的数据模型：

```text
各来源抓取器
    │
    ▼
source-raw/<source>/<date>.json        不可变证据层，仍是事实回放入口
    │  离线标准化；Product Hunt 使用 records 全量底账
    ▼
本地 SQLite catalog                  重建 / 校验 / 回溯工作库（不进 Git）
    ├── products + identities         跨日、跨来源实体与稳定身份
    ├── source_items + observations   来源条目与每次观察
    ├── product_source_first_seen     按产品、来源维护首见/末见
    └── taxonomy_*                    规则或 LLM 版本化分类
    │  导出只读查询投影；分片、幂等、可续传
    ▼
Cloudflare D1 devtrends-catalog       Worker 查询库
    │
    ├── GET /api/v1/sources           数据源目录和可用日期
    └── GET /api/v1/trends            日期 × 任意来源组合 × 分面
             │
             ▼
静态 /trends/ 页面渐进增强            API 成功才显示来源选择器；失败保留旧静态页
```

选中来源集合后，趋势的「首次出现」按该集合内的 `MIN(first_seen_date)` 重新计算，而不是先算全站首见再过滤。这保证排除 Product Hunt 后，某产品后来第一次出现在 Show HN 的日期仍然会被正确计入。来源是普通多选集合，没有 Product Hunt 特判。

全历史实跑结果：读取 5,066 份来源日文件，得到 322,156 条观察、313,175 个产品、315,182 条产品×来源首见记录与 372,996 条分类关系；身份冲突 0。完整本地库约 865MB，D1 只上传趋势所需投影，避免把原始正文和观察 payload 复制进在线查询面。

## 一、现状：后加工只覆盖 10.5% 的产品

趋势模型的唯一输入是日报 JSON：

```js
// scripts/build-site.js:29-56
const reports = dates.map(date => JSON.parse(readFileSync(`raw/${date}.json`)));   // 日报视图
const entities = buildEntityIndex(reports);                                       // 趋势实体索引
const trends = buildTrends(reports, latest, { entities });
```

而 `raw/<date>.json` 是**发布层产物**：`collect.js` 已经做过日期过滤、跨源 / 相似度去重、各来源 `max_items` 截断、GitHub Trending 3 期冷却。也就是说「没进日报的产品」= 没有摘要、没有分类、没有 logo、没有仓库指标、没有详情页、不进趋势。

## 三、目标架构

### 3.1 数据分层

```
source-raw/                    证据层（不可变，不动）
  ↓ 离线 importer
data/catalog/*.sqlite          本地完整工作库（忽略，不进 Git）
  ↓ 趋势投影导出 / 幂等上传
Cloudflare D1                  在线查询库
  ↓ Worker API
/trends/                       静态壳 + 动态来源组合

后续：catalog → 日报投影 / LLM enhancement / 长尾详情页
```

**关键点：**

1. **「全量」= 每个来源的合格产品全集**，与「日报当天展示哪些」彻底分离。准入门槛按源声明，展示选择（上限、3 期冷却、排序）下沉为视图策略。
2. **打标按 `entityKey` 缓存**，不是 `sourceId + externalId`。这是对 `docs/长期架构路线.md` 的一处修正：同一产品的多个来源不该各打一次标；顺带治掉 `enhanced-report.js` 靠「来源名 + 标题 + 作者」字符串匹配、改文案就**静默降级为 raw** 的老问题。
3. **日报降级为投影**，但 `docs/架构方案.md` 的「不把 LLM 塞进建站链」继续成立 —— 产品库是构建前的离线步骤，建站只读。
4. **趋势吃轻量 D1 投影**（`products / product_source_first_seen / taxonomy_terms / taxonomy_assignments`），完整观察与正文留在本地库和证据层，不进建站构建链，也不复制到线上查询库。

### 3.2 混合渲染：核心静态 + 长尾服务端渲染

**动机（实测）：** 详情页若按「有 GitHub 仓库的全部」静态生成 = 22,680 项目 × 2 语言 = **45,360 文件**，免费版上限 20,000 直接撞线；若按「有官网的全部」= **51 万文件**，连付费版 100,000 也不够。而文件数只是表象，真正的代价是**每次 push 全站重建**（实测 `main` 曾一天被推 48 次）。

| | 静态核心 | 服务端渲染长尾 |
|---|---|---|
| 范围 | 最近 7 天日报页（中英）+ **这些日报里的产品**详情页 + 首页 / 趋势页 / 分类页 / 归档 / feed / sitemap / robots / 全部 `data/*.json` 分片 | 其余**有 GitHub 仓库**的产品详情页（约 22,180 个） |
| 规模 | 约 1,000–1,200 页 + 数据分片 | 约 22,180 页，按需渲染 + 边缘缓存 |
| 为什么这样切 | 核心页要最稳、最快、最可抓取，且改动最频繁（每天新日报） | 长尾页改动极少、访问极少，静态化的边际收益最低 |
| 文件数 | 约 2,000–3,000 | +约 256 个数据分片 |
| 构建时长 | 从 42.7s 降到「只渲染核心页 + 算趋势 + 写分片」 | 渲染成本从构建期移到请求期 |

**这样切之后，免费版 20,000 文件上限不再是墙**，详情页可以覆盖全量仓库产品；代价是长尾渲染要吃 Worker 的 CPU 配额（免费版 10ms/请求，付费版 $5/月 30s）→ **混合渲染事实上要求 Workers Paid**，但换来了「22k 页 + 免费的文件数」。既有结论（`docs/架构方案.md` / `docs/长期架构路线.md`）：静态资源请求免费且不限量，所以长尾页只要缓存命中就不计费。

### 3.3 长尾渲染的实现路径（复用现有 Worker 入口）

`worker/index.js` 已经是 Worker 入口（`main` + `env.ASSETS` 绑定），现在接管百度验证文件与 `/api/v1/*`；后续扩成长尾渲染时加入项目路由：

```toml
# wrangler.toml
run_worker_first = ["/baidu_verify_*", "/api/v1/*", "/projects/*", "/en/projects/*"]
```

- **静态 / 动态判定**：构建期产出一份 `core-manifest.json`（核心产品路径集合）。命中 → `env.ASSETS.fetch()` 直出；未命中但路径形状合法（`/projects/<owner>/<repo>/`）→ 走渲染；形状非法 → 真 404（保持现有 404 行为）。
- **数据读取**：趋势查询已经选择 D1；长尾详情页优先复用同一 D1，在确认单页查询与 HTML 渲染的 CPU / 行读取成本后再决定是否把详情 payload 外置到 R2。旧规划里的静态 JSON 分片不再是默认方案，因为它无法自然支持任意来源组合与集合内首见重算。
- **缓存**：Cache API，key 带构建期写入的 `catalogVersion`（数据变了版本就变，旧缓存自然失效），TTL 长；命中即不计 CPU。
- **一致性门禁（最关键）**：渲染器必须同构 —— Node 构建期与 Worker 用同一份渲染函数。验收方式是**同一份输入分别走两条路径，断言 HTML 字节一致**；否则 SEO 会出现「同一页面两种内容」。
- **薄页门禁**：无描述 + 无 star + 无 topic 的长尾页不生成（或 `noindex`），sitemap 只收合格页，控制索引规模。
- **sitemap**：>45,000 URL 时拆 sitemap index（既有结论）。当前 4,490 条。

## 七、风险

- **同构渲染不一致**是最严重的一条：静态核心与 SSR 长尾产出的 HTML 必须字节一致，否则同一 URL 对爬虫与用户呈现不同内容。必须用「同一输入两条路径 diff」当门禁，而不是靠人工抽查。
- **本机是单点**：LLM 打标、交付链、git push 都在这台机器上；31.9 万条按天回溯期间机器不可用就会停在半途（设计上必须可续跑，且「已打标天数」是显式状态）。
- **趋势去噪**：全量入库后 PH 长尾与低分 Show HN 会主导计数。若不做 tier / 来源权重，趋势页会从「开发者趋势」退化成「发布量趋势」。
- **构建期内存**：现在已 935MB 峰值；产品库接入后若直接吃全量会翻倍。轻量投影是硬要求，不是优化项。
- **召回与实体归并**：跨源重合仅 2%，但 PH 底账 24.7 万条没有产品外链，只能按 PH 页面 URL 做实体键 → 同一产品的「PH 发布 + 后来上 Show HN」不会合并。要么接受，要么给底账补 `productLinks`（成本待评估）。
