# DevTrends 产品库与混合渲染规划

> 2026-09-14 讨论产出并开始实施，2026-09-15 按最终渲染边界重排阶段。**状态：MySQL 唯一数据库、全量趋势 API、任意来源组合与日更直写已完成；下一阶段是「可穷举页面静态化 + 产品详情全动态化」。**
> 触发问题：「趋势洞察里的产品是抓取到的全量产品，还是每日日报里展示的展品？」
> 答案：是日报展示的展品（`scripts/build-site.js` 只把 `知识/大家都在做什么/raw/*.json` 喂给趋势模型，那是日报视图）。由此引出两层重构：**后加工与日报解耦（产品库）** 与 **可穷举页面静态化 + 产品详情动态化（混合渲染）**。
> 关系：延伸 `docs/架构重构规划.md`（方案 A 渐进模块化）与 `docs/长期架构路线.md`（版本化 enhancement JSON / source-raw 外置）；**渲染部分推翻 `docs/架构方案.md` 的「不做 SSR」**，并把原先「文件达到 60000–70000 再验证长尾按需渲染」收敛成更清晰的全量详情动态边界。

## 当前落地状态（2026-09-14）

第一批不是再生成一套大 JSON，而是把「证据、事实、内容、发布视图」拆成可迁移的数据模型：

```text
各来源抓取器
    │
    ▼
source-raw/<source>/<date>.json        不可变证据层，仍是事实回放入口
    │  离线标准化；Product Hunt 使用 records 全量底账
    ▼
内存投影编译器                    从证据层直接归一、聚合并校验
    ├── products                       跨日、跨来源实体与稳定身份
    ├── product_source_first_seen      按产品、来源维护首见/末见
    └── taxonomy_*                     规则版本化分类
    │  生成带哈希的分片、幂等、可续传 MySQL 包
    ▼
阿里云 RDS MySQL                   唯一查询库，Worker 经 Hyperdrive 访问
    │
    ├── GET /api/v1/sources           数据源目录和可用日期
    └── GET /api/v1/trends            日期 × 任意来源组合 × 分面
             │
             ▼
静态 /trends/ 页面渐进增强            API 成功才显示来源选择器；失败保留旧静态页
```

选中来源集合后，趋势的「首次出现」按该集合内的 `MIN(first_seen_date)` 重新计算，而不是先算全站首见再过滤。这保证排除 Product Hunt 后，某产品后来第一次出现在 Show HN 的日期仍然会被正确计入。来源是普通多选集合，没有 Product Hunt 特判。

全历史实跑基线：读取 5,066 份来源日文件，得到 322,156 条观察、313,175 个产品、315,182 条产品×来源首见记录与 372,996 条分类关系；身份冲突 0。现在日报链不再落本地数据库，而是在内存中生成趋势所需的 MySQL 投影并幂等上传。

## 一、现状：后加工只覆盖 10.5% 的产品

趋势模型的唯一输入是日报 JSON：

```js
// scripts/build-site.js:29-56
const reports = dates.map(date => JSON.parse(readFileSync(`raw/${date}.json`)));   // 日报视图
const entities = buildEntityIndex(reports);                                       // 趋势实体索引
const trends = buildTrends(reports, latest, { entities });
```

而 `raw/<date>.json` 是**发布层产物**：`collect.js` 已经做过日期过滤、跨源 / 相似度去重、各来源 `max_items` 截断、GitHub Trending 3 期冷却。也就是说「没进日报的产品」= 没有摘要、没有分类、没有 logo、没有仓库指标、没有详情页、不进趋势。

## 三、目标架构

### 3.1 数据分层

```
source-raw/                    证据层（不可变，不动）
  ↓ 离线 importer
scripts/catalog/build-mysql-import.js  内存归一与 MySQL 增量包生成
  ↓ 本地校验 / Hyperdrive 幂等上传
阿里云 RDS MySQL             唯一在线查询库
  ↓ Worker API
/trends/                       静态壳 + 动态来源组合

后续：catalog → 站点快照 / 动态详情 / 日报投影 / LLM enhancement
```

**关键点：**

1. **「全量」= 每个来源的合格产品全集**，与「日报当天展示哪些」彻底分离。准入门槛按源声明，展示选择（上限、3 期冷却、排序）下沉为视图策略。
2. **打标按 `entityKey` 缓存**，不是 `sourceId + externalId`。这是对 `docs/长期架构路线.md` 的一处修正：同一产品的多个来源不该各打一次标；顺带治掉 `enhanced-report.js` 靠「来源名 + 标题 + 作者」字符串匹配、改文案就**静默降级为 raw** 的老问题。
3. **日报降级为投影**，但 `docs/架构方案.md` 的「不把 LLM 塞进建站链」继续成立 —— 产品库是构建前的离线步骤，建站只读。
4. **趋势吃 MySQL 轻量投影**（`products / product_source_first_seen / taxonomy_terms / taxonomy_assignments`），完整正文仍留在不可变证据层，不进建站构建链。

### 3.2 最终渲染边界：可穷举页静态 + 产品详情动态

**动机（实测）：** 详情页若按「有 GitHub 仓库的全部」静态生成 = 22,680 项目 × 2 语言 = **45,360 文件**，免费版上限 20,000 直接撞线；若按「有官网的全部」= **51 万文件**，连付费版 100,000 也不够。而文件数只是表象，真正的代价是**每次 push 全站重建**（实测 `main` 曾一天被推 48 次）。

| | 静态生成 | Worker 动态渲染 |
|---|---|---|
| 范围 | 首页、日报、归档、卡片、趋势总览、全部受控分类列表、feed、sitemap、robots 及它们的中英版 | **全部产品详情页**，不再区分近期与长尾 |
| 为什么这样切 | 页面集合由日期与受控词表决定，构建时可完整穷举，且是最常访问的 SEO 入口 | 数量随产品库无界增长，而单页可由稳定身份定位，适合按需渲染与长缓存 |
| 数据来源 | 每次 MySQL 更新后生成的版本化站点快照 | MySQL 详情投影 |
| 访问 MySQL | 不访问；默认 HTML 与固定范围分片均已预生成 | 首次请求读 MySQL，随后命中 Cache API |

**这样切之后，静态文件数不再跟产品数量线性绑定**。趋势和分类是高频公共视图，用静态请求获得最低成本与最稳定首屏；产品详情是低频、无界长尾，由 Worker 只为真实访问支付首次渲染成本。

### 3.3 产品详情的实现路径（复用现有 Worker 入口）

`worker/index.js` 已经是 Worker 入口（`main` + `env.ASSETS` 绑定），现在接管百度验证文件与 `/api/v1/*`；后续扩成长尾渲染时加入项目路由：

```toml
# wrangler.toml
run_worker_first = ["/baidu_verify_*", "/api/v1/*", "/projects/*", "/en/projects/*"]
```

- **路由判定**：所有合法 `/projects/<owner>/<repo>/` 与 `/en/projects/<owner>/<repo>/` 都进 Worker；MySQL 有实体则渲染，没有则返回真 404。
- **数据读取**：趋势查询已经通过 Hyperdrive 读 RDS MySQL；长尾详情页优先复用同一链路，再按真实 Worker CPU / 行读取成本决定是否把大字段外置到 R2。
- **缓存**：Cache API，key 带构建期写入的 `catalogVersion`（数据变了版本就变，旧缓存自然失效），TTL 长；命中即不计 CPU。
- **渲染门禁**：动态页复用现有详情页的 view model 与 HTML 组件，用黄金样例比对标题、正文、来源历史、canonical、hreflang、JSON-LD 和评论键；切流后不再有静态详情双路径需要长期保持字节一致。
- **薄页门禁**：有稳定身份但内容不足的详情页返回可访问页面并加 `noindex`，sitemap 只收合格页；数据库没有该身份才返回真 404。
- **sitemap**：>45,000 URL 时拆 sitemap index（既有结论）。当前 4,490 条。

## 七、风险

- **快照与 MySQL 版本错位**是最严重的一条：MySQL 已更新但站点快照生成/提交失败时，默认静态页和自定义 API 会短暂处在不同 catalog version。日更链必须把「写库 → 生成快照 → 校验 → 提交」当作一个可重试单元，页面明确暴露版本。
- **本机是单点**：LLM 打标、交付链、git push 都在这台机器上；31.9 万条按天回溯期间机器不可用就会停在半途（设计上必须可续跑，且「已打标天数」是显式状态）。
- **趋势去噪**：全量入库后 PH 长尾与低分 Show HN 会主导计数。若不做 tier / 来源权重，趋势页会从「开发者趋势」退化成「发布量趋势」。
- **构建期内存**：现在已 935MB 峰值；产品库接入后若直接吃全量会翻倍。轻量投影是硬要求，不是优化项。
- **召回与实体归并**：跨源重合仅 2%，但 PH 底账 24.7 万条没有产品外链，只能按 PH 页面 URL 做实体键 → 同一产品的「PH 发布 + 后来上 Show HN」不会合并。要么接受，要么给底账补 `productLinks`（成本待评估）。
