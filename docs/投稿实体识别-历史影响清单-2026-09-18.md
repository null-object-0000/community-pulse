## 怎么读这份清单

A / C / D 三类是**地址根本指错了对象**（图片、徽章、商店页、仓库子页面、官网），改成仓库地址
都是明确改善；E 类多是「正文先提到的底座项目 / 组织页」被换成作者自己声明的仓库；
F 类是显式字段与正文链接指向两个不同仓库，按「显式字段优先」处理，需要人工确认一次。
这 434 行的**旧地址**就是它们的旧产品身份，所以落这批改动会同时影响 MySQL 产品库：
旧身份的产品行不会被 upsert 覆盖（导入只有 upsert、没有撤销），需要配套的定向撤销 / 合并。

## 采用的修正规则

- **显式地址字段优先**：正文里的「项目地址 / 开源地址 / 仓库地址 / 源码地址 / GitHub 地址」等
  显式字段决定仓库身份，优先于正文里的普通链接；「官网 / 官方 / 网站」等只作行链接兜底 ——
  fork、汉化版、二开的投稿会写「官方：<上游仓库>」，那条是上游不是这个产品。
- **冲突不自动归并**：出现 ≥2 个明确仓库地址时进入待审（`status: review` /
  `reason: multiple_project_addresses`），不挂仓库身份，`url` 退回投稿页。
- **修正与撤销配套**：这 434 行的旧地址就是它们的旧产品身份，而导入只有 upsert、没有撤销，
  所以历史修正必须和产品库的定向撤销 / 合并一起做，不能只跑一次 `catalog-refresh`。
