## 架构前提（不再讨论的部分）

保留现有「静态页面 + 动态详情」架构：可穷举的页面（首页、日报、趋势、全部受控分类）在构建期预生成，
只有产品详情页动态渲染（Worker + MySQL + `catalogVersion` 边缘缓存）。**不再混入前端框架迁移** ——
09-11 的三份架构评审已经用成本与复杂度否决了 SSR 与 bundler 路线，本次重构也没有推翻这个判断。

### 2. 修正投稿实体识别

明确的「项目地址／GitHub 地址」字段优先于正文普通链接；多个明确地址冲突时进入待审，不自动归并；
审核历史受影响记录，定向修正产品身份、来源关系和路由；已上线旧路由制定重定向或保留策略。

**验收**：已知错认样例修正；合法关联仓库不被当作主产品；历史合并变化有可检查的 diff。

**核实（09-18，本轮已改代码，未重建历史）**

- 缺陷确认：`source_raw_items.js` 的 `issueItems()` 直接调 `discoverItemRepository()`，而后者在
  没有 `githubUrl`/`websiteUrl` 时取 `extractGitHubRepoUrls(item.content)[0]` ——
  **正文里第一个 github.com 链接**。投稿正文常先提到依赖仓库、参考项目、上游仓库，于是认错产品。
- 改法（三个文件，见 `CHANGELOG.md` 2026-09-18 的第二、三节）：
  1. `issue-description.js` 新增 `explicitProjectUrls(body, labels)`：按行扫描**原始**正文取地址字段
     的值（不能走 `stripInlineMarkup`，它会把裸链接删掉）；先删 HTML 注释（模板示例常带假地址），
     裸链接按中文标点终止。支持「项目地址：URL」与「项目地址」单独一行两种写法。
  2. 地址字段拆成两份：`PROJECT_URL_LABELS`（项目地址/开源地址/仓库地址/源码地址/github 地址…）
     能定仓库身份；`SITE_URL_LABELS`（官网/官方/网站/在线…）**只**作行链接兜底 ——
     因为 fork、汉化版、二开的投稿会写「官方：<上游仓库>」，那条是上游不是这个产品。
  3. `normalizeGitHubRepoUrl(value, { allowSubpath: true })`：作者自己写的 `/releases`、
     `/tree/main/<子目录>` 取仓库根；默认行为（拒绝子路径）不变，`D.repository` 那侧不受影响。
- **量过再改**：全量投稿语料（`weekly-issues` + `hellogithub-issues`，5,847 行）
  新旧逐行对比 —— **30 行 url 变化、18 行仓库身份变化**，逐条核对全部是「改成作者自己声明的地址」：
  例 #6110 `dzhng/deep-research` → `AnotiaWang/deep-research-web-ui`（正文先提到它复刻的上游）、
  #7071 `resolver-vs-graphql` → `pydantic-resolve`、#7728 `txstc55/ugly-avatar`（参考项目）→
  `xingxingc/stray_avatar`、#7989 `yihong0618/running_page`（参考）→ `chempeng/reading_page`、
  #10761 `bytedance/flowgram.ai`（底座）→ `boommanpro/gaia-workflow-engine`；
  #7164 gemini-cli 汉化版**保持不变**（`官方:` 指上游，被排除在仓库判定之外）。
- 冲突（≥2 个明确仓库地址）只有 **3 行**（#9615 OpenToggl 两仓、#11358 三个 skills 仓、
  HelloGitHub#3510 四个 goto-* 仓）。按计划「不自动归并」：不挂仓库身份、`url` 退回投稿页、
  记一条 `status: review / reason: multiple_project_addresses`。代价是这 3 行的产品身份从
  `github:` 变成 `url:`，重建后 MySQL 里的旧行不会被 upsert 覆盖（只有 upsert、没有撤销）——
  要和第 1 项的撤销通道一起处理。
- **要生效必须重建**（本轮只改了归一化代码，`raw/*.json` 与 MySQL 还是旧投影）：
  写了 `scripts/backfill_issue_entity.js` 做**定向回填**（不重跑 collect —— `raw/*.json` 里没有
  当时的 Trending 观察日，老文件连 `sourceRaw` 都没有，重跑会换掉 Trending 那一整段数据，
  而且今天的规则会顺带重算历史简介与配图）。干跑结果比原先估计大得多：
  **434 行、198 个日报日**（不是 18 行）—— 因为老 raw 文件是**更早的代码**写的，行的地址本身就
  指错了对象：195 行是图片 / 徽章 / 商店页（`github.com/user-attachments/...`、`img.shields.io`、
  Chrome 商店…），216 行是官网（没认出仓库），15 行是仓库子页面，7 行是「正文先提到的底座项目 /
  组织页」，1 行是显式字段与正文冲突。另有 251 行只错在 URL 形态（尾部中文标点）。完整清单见
  `docs/投稿实体识别-历史影响清单-2026-09-18.md`。
  - **代价（这是没有一次落地的原因）**：这 434 行的旧地址就是它们的**旧产品身份**，而 MySQL 导入
    只有 upsert、没有撤销 —— 落这批改动会新增约 434 个产品、同时把旧身份的产品留成孤儿
    （其中「官网 → 仓库」那 216 行会让同一个产品在库里出现两份）。所以历史修复要和第 1 项的
    定向撤销通道合成一件事做，不能只跑一次 `catalog-refresh`。

### 3. 自动化快照与缓存发布收尾

固定执行顺序：写库成功 → 强制生成快照 → 校验 → 提交 → 部署 → 冒烟；验证静态快照、Worker 版本与
动态详情数据一致；增加详情缓存失效策略，不再依赖手改渲染版本；失败时保留明确状态，允许从故障步骤续跑。

**验收**：同一天回填也能产生有效新版本；部署后规范化详情地址立即展示新内容；失败不被报告为成功。

**核实（09-18，部分完成）**

- 已经有的：`catalog-refresh.yml` 的 `refresh_snapshot` 默认 **true**（跳过同版本快照缓存），
  `build-site-snapshot.js` 的 `--refresh` 注释也写清了「MySQL 变了但 `--to` 没变时必须开」；
  日更 workflow 的 `--to` 每天推进，所以日更天然换代；`catalogVersion` 是**内容哈希**
  （sources + 趋势模型 + 分类文件 + 路由），不是日期字符串。
- **本轮修掉的**：详情页缓存键第二段原本是 `worker/index.js` 里手改的
  `PRODUCT_RENDERER_VERSION`（09-17 的投稿标签修复、09-18 的详情行重建都靠手工 `+1` 收尾，
  忘了改就线上最长 24 小时读旧渲染）。现在由 `scripts/render-version.js` 对渲染链路源码
  （`worker/index.js`、`project-page.mjs`、`mysql-db.mjs`、`catalog-api.mjs`、`web/shared.js`）
  取哈希生成 `worker/render-version.mjs`，`npm run build` 时重新生成 —— 改渲染逻辑必然换代。
  三条测试钉住：提交的值与源码一致、任一渲染源变化必然改哈希、`worker/index.js` 不许再硬编码版本。
- **还差**：两个 workflow 都没有部署后的冒烟步骤（现在靠人肉 curl）。建议加一步
  「轮询线上详情页 + `/api/v1/sources`，比对 `catalogVersion` 与本地快照一致，失败即红」，
  与 `search-index.yml` 已有的「轮询到线上出现再推送」是同一个模式。

### 4. 接通增强自动补偿

在能访问 LLM 的增强主机上定时检查近期缺失任务；数据迟到、网络失败后自动续跑，但不重复发送日报；
区分增强、提交、推送、交付四种状态；去除发送脚本任意将 `HEAD` 推到 main 的风险；
对持续失败、增强覆盖不足发出告警。

**验收**：模拟 raw 迟到和 LLM 中断后能恢复；既有完整 final 不被覆盖；不会误推开发分支或重复发消息。

**核实（09-18，仓库侧已备好，主机侧未接）**

- 仓库侧两件都在：`scripts/check-enhancement.js`（`pendingDates()` 找超过宽限期的缺失增强，
  `--repair` 会真的调 `enhance-report.js`）、`.github/workflows/enhancement-watchdog.yml`
  （每小时跑一次，只告警：缺 `--repair` 时退出码 1 → workflow 变红）。
- **缺口 1**：增强主机上的 `~/.hermes/profiles/communitypulse/scripts/community_pulse_send.sh`
  从不调用 `check-enhancement.js --repair`，所以「告警有、自动补偿没有」。09-15 那次缺失的根因
  也已经查到：发送任务第一步 `git pull` 因 TLS 握手失败退出（当时日更还没提交 raw，LLM 根本没跑），
  10:17 补跑成功后没有任何补偿触发。
- **缺口 2**：同一个脚本第 4 步用 `git push origin HEAD:main`（注释里也承认「仓库常被其他工作线
  checkout 在功能分支上」）—— 把当前 HEAD 推到 main 意味着在功能分支上运行会把功能分支推上生产。
  它每次都跑在 `$REPO` 这个共享 checkout 上，所以这是真实风险，不只是理论问题。
- 这两处都在**仓库之外**（`~/.hermes/...`，不受版本控制），改它会影响次日 07:30 的发送，
  所以留作待确认项：建议 ① `--repair` 改为独立 cron 任务而不是塞进发送脚本（避免发送流程变慢、
  也避免补偿失败连带影响发送）；② 推送改成显式校验「当前分支是 main 且与 `origin/main` 无分叉」
  再推，或改为在临时 worktree 里操作。

## 第二阶段：全量产品证据补全

### 5. 证据采集与日报截断解耦

仓库信息、官网描述和 logo 的候选不再受日报 `max_items` 限制；按产品去重抓取，保留成功、缺失、
失败和重试时间；按来源与日期测量证据覆盖率；历史回填分批执行，不伪造不存在的历史观察值。

**验收**：完整产品底账都经过证据候选判断；失败可续跑；缺证据和没执行能明确区分。

### 6. 重建受影响的 MySQL 展示投影

用补全后的证据重算详情、分类列表和可索引性；使用现有全量详情重建通道
（`catalog-refresh.yml` 的 `full_rebuild=true`），避免旧评分挡住修正；检查图片地址本地化、
标题兜底和摘要选择的一致性。

**验收**：日报、分类、详情对同一产品展示一致；薄页判断有真实内容依据；图片引用可渲染。

## 第三阶段：MySQL 原生翻译与分类

### 7. 建立产品级 LLM 加工流水线

用稳定 `product_id + 输入哈希` 定位任务，不再依赖 Markdown 标题；在 MySQL 保存任务状态、结果、
模型／提示词／分类体系版本；支持限流、退避、断点续跑和失败重试；只对输入变化或加工版本变化的
产品重跑；源内容为空时保留空值，不编造描述或分类依据。

### 8. 分批回填并接入消费端

顺序：① 已进入日报的产品 → ② 最近 12 周产品 → ③ 更早历史产品。详情页、趋势统计和快照统一消费
同一份加工结果，不再各自推断一套分类。

**验收**：有充分证据的产品具备双语摘要和受控分类；低证据产品明确标为未分类；新任务失败不破坏
上一版有效结果。

### 9. 重新验收趋势统计口径

明确去重实体、来源组合下首次发现日期、父子分类合计规则；明确「占比」的分母，以及多标签是否允许
占比相加超过 100%；同时展示分类覆盖率，不能把未知类别当成不存在；对小说创作等样例人工复算，
比较静态快照与自定义 API。

**验收**：能可靠回答「最近一周有多少产品属于小说创作」，并明确未知数据对结论的限制。

## 第四阶段：日报统一为产品库投影

### 10. 建立结构化日报发布记录

把日报选品、顺序、冷却规则、持续热门和当期加工版本保存为结构化发布记录；日报 JSON、Markdown 和
HTML 从该记录派生；已发布日报固定其版本，不随产品库更新悄悄改写历史内容。

### 11. 双跑切换旧链路

新旧流水线并行输出到独立目录；对历史日报逐字段比较，解释所有差异；验收后统一图片、评论、搜索推送
等输入；最后退役 `raw + final` 的主数据职责，保留历史兼容读取。

**验收**：日报顺序、冷却、双语、评论键、SEO 和下载入口不丢失；Markdown 不再承担结构化增强存储。

## 第五阶段：契约、存储与维护性

### 12. 建立跨层数据契约

为证据 envelope、标准化 item、产品、增强结果、日报、快照建立版本化 Schema；引入类型检查，
先约束跨层接口；未匹配、重复身份、覆盖异常必须显式失败或告警，不能静默降级。

### 13. 注册表驱动采集与局部重跑

注册表统一来源 adapter、日期策略、校验器和消费配置；抽出通用重试、原子写入、哈希和断点续跑能力；
支持按来源、日期和步骤局部重跑，逐源迁移而不是一次重写。

### 14. 将 source-raw 外置 R2

## 写生产之后的核对纪律（本轮新增）

- **Hyperdrive 读缓存是 `max_age=300` + `stale_while_revalidate=900`**：写完立刻查会读到最长 5 分钟（SWR 下 20 分钟）之前的结果。本轮因此误判两次（撤销后广告页仍 200、补齐导入后产品页仍 404）。核对要么等过窗口，要么换一个等价 pathname。
- **详情页缓存键** = `CATALOG_VERSION + 渲染源码哈希 + pathname`，`s-maxage=86400`。撤销数据后规范地址可能还返回旧状态，换等价 pathname（`/PRODUCTS/<id>/`）立刻能看出是缓存；要立刻清掉就改一次渲染源文件让哈希换代。
